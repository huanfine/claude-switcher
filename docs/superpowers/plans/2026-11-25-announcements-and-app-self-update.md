# 公告功能 + App 自动更新机制 实施方案(2026-11-25)

> 目标:公告从「App 内写死的静态页」变成「发布端可更新、用户端定时拉取」的动态机制;
> App 二进制纳入自动更新(现状:自动更新只覆盖核心脚本,App 只能重跑安装器)。
> 本文档是实施方案,不含完整代码;每步标注落点与参考思路,照 AGENTS 纪律执行
> (功能/数据/环境分层、探测失败明确报错、当天推送)。

---

## 1. 目标与范围

### 公告功能
- 维护者在仓库里改一个 JSON 文件即完成发布公告,零新增基础设施(发布渠道复用 GitHub)。
- 用户端:启动与定期拉取 → 本地缓存 → 公告页展示;未读公告在入口图标上显示红点;
  critical 级公告在启动时弹一次,确认前不静默。
- 明确不做:不做任何回传(无已读上报、无统计埋点),保持「本地工具、单向拉取」定位;
  不做推送通知(不注册系统通知权限)。

### App 自动更新
- 把 App 二进制(+ Info.plist / version.txt 版本元数据)纳入既有 `update --auto` 链路:
  12 小时周期检查 → 发现有新版 → 下载发版包 → 校验 → 原子换装 → 自检失败自动回滚。
- 明确不做:不做差量更新(发版包本就几 MB,全量+哈希校验足够);不做多通道
  (stable/beta 分流),单一通道跟 main 发布;不在检查/修复/切换进行中触发换装。

### 非目标(边界声明,写进文档防蔓延)
- 商业化兼容:协议保持 MIT,方案不引入任何闭源组件依赖;更新源 URL 做成常量,
  未来若商业化换自有源,只改一处。
- 老版本兼容线:能从「无 version.txt 的手装形态」平滑升级到新机制(见 §5)。

## 2. 核心流程与架构分工

沿用仓库既有分层,不许跨层:

```
发布端(维护者)          核心脚本(功能层)                App(展示层)              守护
─────────────          ──────────────────            ─────────────           ──────────
改 announcements.json   fetch-announcements:           只读缓存文件渲染          update --auto
改版本号→tag→CI发版  →  下载→校验→写缓存+TTL      ←  公告页=静态边界段       每12h:
                        (复用 update 的拉取+              + 动态公告列表            ① 核心脚本更新(现有)
                         哈希校验骨架)                    未读→红点/critical弹窗   ② App 自更新(新增)
```

原则:
1. **网络请求只发生在核心脚本**,App 永远不自己 fetch——与 rtt.log / incidents.log
   的「脚本写、界面读」模式一致。
2. **App 自更新由 LaunchAgent 驱动、核心脚本执行**,App 自身只负责「重启自己」
   (退出→等新进程被拉起),不参与下载与换装,避免「正在运行的程序替换自己」的
   半截文件问题。
3. 所有判定 fail-open:拉不到、校验不过、缓存过期 → 用旧缓存或不展示,**绝不阻断
   启动、绝不误杀 Claude**。

## 3. 公告发布和读取规则

### 3.1 发布端(数据层:仓库内单文件)

- 文件:`data/announcements.json`(与 `claude-rules.json` 同目录同待遇,进 git,发版随包)。
- 结构(字段固定,新增字段向后兼容、App 忽略未知字段):

```json
{
  "schema": 1,
  "updated_at": "2026-11-25T12:00:00Z",
  "items": [
    {
      "id": "2026-11-25-dns-leak",          // 稳定 ID,已读判定的唯一键
      "severity": "info",                    // info | warn | critical
      "title": "第 16 项已换成「DNS 泄露」检测",
      "body_md": "……(轻量 Markdown:粗体/链接/换行,渲染白名单内)",
      "min_app_version": "1.8.12",           // 低于此版本才显示(引导升级用),可空
      "max_app_version": "",                 // 高于此版本不再显示(过期公告),可空
      "expires_at": "2027-02-01T00:00:00Z",  // 服务端过期,可空
      "link": ""                             // 可选,「了解更多」外链
    }
  ]
}
```

- **发布流程 = 改这一个文件 → 提交推送**。CI 不需要新步骤;可选在 CI 里加
  JSON schema 校验(缺 id/severity 即拒),防手滑发坏数据。
- **完整性边界(诚实声明,照 SECURITY.md 口径)**:内容源 = 本仓库 main 分支,
  信任根 = GitHub 仓库本身,传输层 = HTTPS。与现有 SHA256SUMS 同一信任边界——
  仓库账号被攻陷时公告内容会被一并替换,这是当前信任上限,不额外做签名机制
  (公告非可执行内容,展示层对 body_md 做白名单渲染,注入面可控)。

### 3.2 读取端(功能层:核心脚本)

- 新增命令 `announcements check`(供 App 调用与 LaunchAgent 低频调用):
  1. 读 env.json 确认在线(cache 命中则跳过网络);
  2. GET 更新源(常量:raw.githubusercontent.com/main 的该文件路径;
     失败依次回退 jsDelivr CDN → 本地缓存,逐级降级并在结果里标注来源);
  3. 校验 schema(JSON 可解析、schema 匹配、items 为数组),坏数据**明确报错不静默**;
  4. 按本机 App 版本过滤 `min/max_app_version`,按 `expires_at` 过期剔除;
  5. 写缓存 `~/.claude-switcher/announcements-cache.json`(0600),附带
     `fetched_at`(用于 6 小时 TTL 判断)与 `source`。
- **频控**:App 启动时调一次;运行期由既有 check 流程顺带调用,但内部限流
  ——距上次成功拉取 < 6 小时直接用缓存。绝不按 10 秒巡检周期打网络。
- 与 `sync-rules.py` 同理,公告文件格式变更必须同步 bump `schema` 并更新两端校验。

### 3.3 展示端(界面层:App)

- 公告页 = 两段式:上半部分保留现有「安全边界说明」静态内容(措辞按已批准的
  去营销化改写落地),下半部分为动态公告列表(按 severity 排序:critical > warn > info)。
- **未读判定**:公告 id 的 sha256 存 `~/.claude-switcher/announcements-seen`(0600)。
  缓存里存在、seen 里没有 → 未读:入口图标红点;点开公告页即整批标记已读。
- **critical 级**:启动完成后弹一次公告页(不阻断加载,可关闭);用户点「知道了」
  才写入 seen;不写 seen 则下次启动再弹一次,至多弹到 `expires_at` 过期。
- **info/warn 级**:仅红点,永不弹窗。
- 「不再显示此公告」单条按钮 → 该 id 独立加入 seen 的 `dismissed` 列表(区分
  「读过」与「不想再看」)。

## 4. 自动更新触发条件与边界

### 4.1 版本比较

- 本机 App 版本:App bundle 的 `CFBundleShortVersionString`(Info.plist)。
- 远端最新版本:发版 tag 的 `VERSION` 文件(package-macos.sh 已随包写入,现成数据源;
  备选 GitHub `releases/latest` 302 重定向,免 API 认证)。
- 比较规则:语义化比较(`1.8.13-dev` 拆数字段比较);相等或本机更新 → 不动作;
  远端更新 → 进入下载流程。
- version.txt 同步:`update` 流程每次替换核心脚本后,把新版本号写入
  `~/.claude-switcher/version.txt`(0600)——补上「手装形态没有 version.txt」的坑,
  报告的 `core_version` 不再是 unknown。

### 4.2 触发条件(全部满足才动手)

| 条件 | 说明 |
|---|---|
| 周期到达 | 既有 LaunchAgent 每 12h,`update --auto` 内新增 App 检查步骤,不新增守护 |
| 版本落后 | 见 4.1 |
| 设置开关 | `checks.json` 同级新增 `app_auto_update`(默认 **开**,用户已明确要「保持最新」);App 设置页提供开关 |
| 空闲判定 | 复用现有 busy guard:检查/修复/账号切换进行中 → 本轮跳过 |
| 磁盘余量 | ≥ 500 MB(发版包 + 解压 + 旧版备份的余量) |
| 下载校验通过 | sha256 与随包 `SHA256SUMS-release.txt` 一致,否则丢弃重来一次,再失败即放弃本轮 |

### 4.3 换装流程(原子性是硬要求)

1. 下载 full.zip 到临时目录 → 校验哈希 → 解压(含 `xattr -d com.apple.quarantine`,
   与 INSTALL.command 现有做法一致,避免下载通道引入 Gatekeeper 拦截);
2. 旧 bundle 整体改名留作 `.old` 备份(同盘 rename,原子);
3. 新 bundle rename 到位(原子)——**任何时刻磁盘上都存在一个完整可启动的 bundle**,
   这就是上游 `7b0fd64` 修「半截文件」的同款思路,应用到 bundle 级别;
4. Info.plist / version.txt 版本号随包就位,不需要事后补写;
5. 提示用户重启 App(不在脚本里 kill 正在运行的界面进程;App 下次启动即新版)。
   可选增强:App 检测到「bundle 已换、自身是旧进程」时提示「重启以完成更新」。

### 4.4 回滚

- 换装后跑最小自检:新 bundle 二进制存在且可执行、`codesign -v` 通过、
  Info.plist 版本号 = 目标版本。
- 任一不过 → 删新留旧(`.old` 改回原名),写 update.log,本轮判失败;
  连续 2 轮失败 → 自动更新 App 通道静默停用并写日志(防止发版事故反复重试),
  需用户手动跑一次安装器或 `update` 重置。这条是「自动更新事故熔断」,照
  SECURITY.md 的诚实口径写进文档。

### 4.5 明确的边界(不做什么)

- 不在脚本里强杀正在运行的 App/Claude;
- 不做差量、不做 beta 通道、不做多源镜像(失败即等下个周期);
- 协议保持 MIT,下载源 URL 是功能层常量,商业化换源只改一处;
- 核心脚本更新(现有链路)与 App 更新是两个独立步骤,各自校验各自回滚,
  互不阻塞——App 下载失败不影响核心脚本照常更新。

## 5. 异常和兼容处理

| 场景 | 处理 |
|---|---|
| 手装形态无 version.txt(本机现状) | App 更新流程启动时先补写 version.txt;`app_version()` 读不到时维持「unknown」不猜 |
| Info.plist 版本号缺字段 | 视为 0.0.0,直接走「有新版」路径完成一次换装即自愈 |
| announcements.json 拉取失败/超时 | 回退 jsDelivr → 本地缓存;全失败不展示,公告页只剩静态段;记日志,不计 fail |
| 缓存 JSON 损坏 | 删缓存重新拉;再失败当「无公告」,照 AGENTS「明确报错不静默」给日志 |
| 用户长期离线 | 公告用最后缓存(TTL 过期仍展示但标注「缓存于 X 日」);更新自然不触发 |
| 发版包下载被代理中断 | 哈希不过 → 重试一次 → 放弃本轮,12h 后自然重试;不打断用户 |
| 老核心不认识新命令 | `announcements`/App 更新步骤对旧核心做存在性探测,不存在则跳过该步骤并记日志(照 `update-check` 对旧核心安全退出的先例) |
| App 更新期间用户双击启动 | busy guard + 原子换装保证:要么旧版完整,要么新版完整;最坏情况用户启动的是旧版,下周期再更 |
| 发布端发坏 JSON | schema 校验拒载 + CI 校验兜底;用户端看到「公告暂不可用」,不影响其他功能 |
| critical 公告滥用防线 | 发布纪律写进 AGENTS:critical 仅用于安全类强提醒;展示层对 critical 弹窗加「每天至多一次」限频,防发布事故变成弹窗轰炸 |

## 6. 验收标准

### 公告功能
1. 发布端:改 announcements.json → 推送 → 用户端 6 小时内可见(或重启 App 立即可见),无需发版;
2. 负例:JSON 缺 id / severity 非法 → 端到端「公告暂不可用」,其余 16 项检查不受影响(测试断言);
3. 已读:红点 → 打开公告页 → 红点消失;「不再显示」的公告跨重启不复现;
4. critical:启动弹一次,关闭不点「知道了」→ 下次启动再弹一次;点「知道了」→ 不再弹;
5. 频控:同一小时内多次触发 check,网络请求日志里 fetch announcements 至多 1 次;
6. 全程零上传:抓包确认只有 GET,无任何 POST/上报(测试环境断言或抓包记录入档)。

### App 自动更新
1. 端到端:本地造一个高版本号的测试发版包 → `update --auto` 完成下载/校验/换装/回执,
   重启后 App 为新版,Info.plist 与 version.txt 均为新值;
2. 回滚:故意给损坏的 zip → 校验失败,旧 bundle 完好可用,update.log 有失败记录;
3. 原子性:换装过程中任意时刻 `open` 该 App 都能启动完整版本(对照测试:换装中途读 bundle,
   内容始终完整——这条钉住「半截文件」不复发);
4. busy guard:检查进行中触发 update → 本轮跳过并记日志;
5. 熔断:连续两次换装失败 → 第三轮不再尝试,日志写明「通道已停用,需手动更新」;
6. 兼容:无 version.txt 的手装环境走一遍全流程 → 平滑补齐,报告 core_version 不再是 unknown;
7. 既有测试全绿:全量 Python 套 + gen-sums + CI。

## 7. 落地顺序(建议三步走,每步独立可交付)

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **一(先做,纯增量)** | 公告功能:数据文件 + schema 校验 + `announcements check` 命令 + App 动态渲染 + 已读机制;顺带落地公告页「去营销化」改写(已有批准稿) | 无新基础设施,纯读 |
| **二** | update 链路扩展:版本比较 + version.txt 补写 + App 下载/校验/原子换装/回滚/熔断 | 阶段一的版本比较逻辑 |
| **三(收尾)** | 设置页开关(app_auto_update)、CI 公告 schema 校验、验收清单逐条跑一遍 | 一+二 |

**关键参考实现**(仓库内现成骨架,不另起炉灶):
- 拉取+校验+回滚骨架:`update` / `update-check`(SHA256SUMS 校验、.bak 备份、自检回滚全部现成);
- 「脚本写、App 读」模式:rtt.log / incidents.log / last-report.json;
- 设置项读写:`get-check-config` / `set-check-config`(新开关沿用同一文件与校验框架);
- 原子换装思路:上游 `7b0fd64`(思路参考、自研实现,MIT 仓库不搬 AGPL 代码);
- 隔离测试模式:`tests/test_probes.py` 的假 curl + 提取函数 harness,公告与更新的
  负例(坏 JSON / 损坏 zip / 断网)全部在 harness 里做,不碰真实网络。
